# 口袋果园花期展图（orchard）

构建在 `confcat` 受限 YAML 目录 + CSV 消费仓之上的应用层。把每株的开花日志、
供粉日段、受粉日段与冷天补记**当作真实 CSV 接入任务**读入，用**当时版本的列来源**
定位补记，归出**相容的整园花期表**，再结合实地床位判定可挂牌承诺。规模：六株、五床、四天以内。

## 数据模型

四份 CSV，各是一个关注点（预算成 confcat 多文档产品的四个文档）：

| 关注点 | 列 | 含义 |
| --- | --- | --- |
| `bloom` | `tree,region,day,bloom` | 每株每天是否开花（片区在此声明） |
| `provide` | `tree,day,provide` | 供给花粉的日段 |
| `receive` | `tree,day,receive` | 接受花粉的日段 |
| `cold` | `region,day,cold` | 冷天断言（每行“是否发生”） |

布尔值接受 `yes/true/1/是/y` 为真。

## 关键语义

**① 用当时版本的列来源定位补记**（`ingest.locate_record`）
每条归一化记录的“原 CSV 列名 + 表头行号”来自任务创建时版本的 column lineage；
“配置来源行”来自列映射键的 provenance。承诺的每条支撑记录都带这三样，可回查。

**② 冷天归并**（`observation.reconcile_cold`）
- 断言按 `(片区, 天)` 归组；同日“发生”与“没发生”并存即抛 `ColdRevisionConflict`，
  携带 `day` 与 `occurred_ref`/`absent_ref`（即“缺的是哪一天哪一边”）。
- 延迟按片区统计**不同发生日历天**：同一冷天被两次复跑各记一次“发生”只算一次；
  不可能“既当成发生又当成没发生”（矛盾断言直接判冲突）。
- 同片区各株一起迟相同天数；整园表里日期平移，支撑记录仍以**原始日**索引。

**③ 承诺**（`commitments`）
一天可挂牌需同时满足：受体当天开花且可受、供体当天开花且可供、两株床距 ≤ 1 且不同位。
一株可同时照应左右两株；自己不作伴。缺日/缺边由 `MissingSide.describe()` 指明，例如
“第 2 天缺乙可供粉”。

**④ 两条交付路线，一份承诺**（`layout`）
- **固定床位图**：花前固定。对片区**尚可能出现的冷天**（片区子集情景）重算，要求承诺
  树对/方向不变（日期可平移）。跨片区树对若“单独遇冷只迟一边”会错开，故不进永久图。
- **带轮盆树**：早班看真实花况后逐日换位。约束：**已开放通道累计不可穿越**（盆只能在
  初始连通段内挪动）+ **每日搬运上限**（当日换床位盆数）。换位评分含“潜在可挂牌对的
  总床距”爬坡项，使需两步才能相邻的树对也能逐日逼近。

## 复跑两次更正

`exhibit.replay_revisions(catalog, repo, initial_csv, [rev1_csv, rev2_csv], num_beds)`
依次为初始与每份更正**发布新配置版本并建全新归档任务**，返回每一步的任务号、整园表与展图。
每轮任务绑定各自版本（v1/v2/v3…），可独立回查，是真正“从实际归档任务复跑”。

## 运行

```bash
python3 demo/orchard_demo.py                      # 端到端演示（含全部断言）
python3 -m unittest tests.test_orchard -v         # 果园层测试
```

## 文件

```
orchard/
  ingest.py         # 四类关注点接入任务 + 当时版本列来源定位补记
  observation.py    # 冷天归并（冲突指名哪一天哪一边）+ 相容整园花期表
  commitments.py    # 方向正确交集 + 床距<=1 + 缺日/缺边诊断
  layout.py         # 固定床位图（冷天稳健）与带轮盆逐日换位（通道+上限）
  exhibit.py        # 编排/渲染/交付 + 从实际归档任务复跑两次更正
  samples/          # 示例 CSV（含 rev1 冷天更正、rev2 供期更正）
```
